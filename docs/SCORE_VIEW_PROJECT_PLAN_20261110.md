# 谱面视图（听歌可视化）项目企划书

日期：2026-11-10 · 状态：拆分完成，阶段一待开工 · 代码目录（拟）：`source/scoreview/`

参考画面：B 站《15 Step》导赏视频的一帧——多轨音符从右向左流过一条播放线，上方是当前和弦和一句导赏文字，下方是段落章节条。

## 1. 目标与完成定义

播放一首已分析的歌时，屏幕上有一张**跟着音乐走的多轨谱面**：人声、乐器、鼓的音符流过播放线；上方显示当前和弦与"现在该听什么"的提示；下方显示歌曲走到了哪一段。

- **载体是实时播放页面，不是视频。** 参考画面的载体是视频，但目前没有发布计划，所以评判标准只有一条：我自己听歌时好不好用。视频导出不在范围内（见 §8）。
- **阶段一完成** = 两首试点曲目在试听页上具备参考画面里所有做得到的元素，且每一层都被眼睛和耳朵验收过。
- **阶段二完成** = 在 XML 里任选一首已分析的歌都能进这个视图；缺哪层数据就少画哪层，不报错。

它不替代 XLD 的时间轴。时间轴是**标注和修订**用的工作面；谱面视图是**听歌**用的呈现面，只读。

## 3. 现状盘点（2026-11-10 实测）

### 3.1 三个现成的可视表面

| 表面 | 是什么 | 对本项目的意义 |
|---|---|---|
| **XML（Fusion）** `source/fusion-runtime-baseline` | 项目里"消费 XLD 分析结果的音乐可视化"那一半。自带播放器（知道曲目和播放位置）、能切分轨、已通过 `xld-timeline-provider-adapter.js` 拿到"当前段落 + 多引擎共识和弦"。场景全是抽象画面（频谱、脉冲星、MilkDrop、Glitch），**从没画过音符**。工作区里源码干净，无未提交改动。 | 谱面视图最自然的家（§4 D1） |
| **XLD 时间轴** `timeline-controls.js` | 段落 / 和弦 / 各声部音符同轴显示，可图上标注。播放线靠 `timeupdate` 驱动（一秒约 4 次，不够顺滑）。文件上压着大量未提交改动。 | 标注面，不动它 |
| **音色工作台** `source/memesynth/studio` | 本地网页（localhost），浏览器内 JS 引擎即时切换八套音色与人声。 | "本地网页 + 试听页发 Artifact 手机验收"这套做法直接沿用 |

### 3.2 数据覆盖率

对开发版共用的分析根（`artifacts/refinement-three-20260915/analysis`，18 首）逐首清点：

| 层 | 覆盖 |
|---|---|
| 声部音符（bass / drums / guitar / piano / strings） | 16 / 18 |
| 和弦（任一引擎） | 6 / 18 |
| 段落（SongFormer） | 3 / 18 |
| 段落 + 和弦 + 至少三个声部齐全 | **3 / 18**（Mirrors、Ceremony、MEGURI） |
| 人工标注 | 0 条 |
| 人声音符 | 0 / 18 |
| 节拍网格 | 0 / 18 |

七里香——下游工作做得最深的一首——在分析根里只有五个声部的音符，没有和弦也没有段落。

### 3.3 结论

**画出来是容易的一半，数据覆盖是难的一半。** 渲染一张滚动谱面是标准前端工作；但参考画面的十一个元素里，今天全库都拿得出数据的只有四个。所以拆分分两个阶段：阶段一用手工配齐的两首歌证明"这个画面配上我们的数据好不好看"，阶段二才处理"任意一首歌都能进"。

## 5. 架构

三样东西，彼此只通过一个数据对象相连。

**谱面模型**（契约 `xin.score-view/1`）——渲染所需的全部数据，时间一律是秒，零点是音频零点：

```json
{
  "contract": "xin.score-view/1",
  "track":    { "id": "", "title": "", "artist": "", "album": "", "duration": 0 },
  "audio":    { "src": "", "offset": 0 },
  "lanes": [
    { "id": "vocals", "label": "人声", "kind": "melody",
      "notes": [[0.0, 0.5, 59, 96]],
      "contour": { "hop": 0.01, "start": 0, "midi": [59.1, null] } },
    { "id": "guitar/clean electric guitar", "label": "电吉他", "kind": "pitched", "notes": [] },
    { "id": "drums", "label": "鼓", "kind": "drums",
      "rows": ["kick", "snare", "hihat", "openhat", "tom", "crash", "ride"],
      "hits": [[0.0, 0, 110]] }
  ],
  "chords":   [[0.0, 4.2, "D#m", 0.78]],
  "sections": [[0.0, 21.0, "引子", "songformer"]],
  "bars":     { "beatsPerBar": 4, "beats": [], "downbeats": [], "steady": true },
  "captions": [[143.0, 149.0, "再回到主歌，先听人声和吉他重新接上。", "manual"]],
  "energy":   { "hop": 0.1, "db": [] }
}
```

`notes` 是 `[起点, 时长, 音高, 力度]`，`hits` 是 `[时刻, 行号, 力度]`。**除 `track`、`audio`、`lanes` 外每个键都可以缺**，缺了那一层就不画——这是阶段二"任意曲目都能进"的前提，从第一天就这样定。

**渲染核心** `score-view.js`——`create(canvas, model, clock)`。纯 Canvas 2D，无依赖，无构建步骤，不知道自己被谁加载。只做一件事：给定模型和"现在几秒"，画一帧。

**宿主**——提供音频、时钟和模型。阶段一是试听页（单文件 HTML，可发成私有 Artifact 在手机上验收）；阶段二是 XML 的场景。两个宿主加载同一个渲染核心，后面每加一层，两边同时获得。

## 6. 工作包

每个工作包以**一个能看能听的试听页版本**结束，带一组只有眼睛和耳朵能回答的验收问题。同一个链接递增版本，页面里记录验收结论。

## 7. 顺序与依赖

```
A0 ──> A1 ──[闸门一]──┬──> A2 ──[闸门二]──> A5 ──[闸门五]──┐
                      ├──> A3 ──[闸门三]                   ├──> 决定点 D1 ──> B0 ──> B1 ──> B2
                      └──> A4 ──[闸门四]───────────────────┘
```

A2、A3、A4 都只依赖 A1，互不依赖。默认顺序 A2 → A3 → A4：A2 最便宜（MEGURI 数据现成），A3 是画面的主角（人声曲线），A4 最开放放最后。闸门一的结论可能改变后面所有包的做法（比如"只留三轨"），所以闸门一之前不往下做。

## 8. 不做的事

- **不做视频导出。** 没有发布计划（C1）。
- **不解决强拍识别。** 那是 downbeat 项目；这里只消费它的结果。
- **不做编辑。** 谱面视图只读；改音符、改标注回 XLD 时间轴。
- **阶段一不碰 XLD 和 XML 的源码，不写分析根。**
- **不做"拍手"轨**，数据里没有这个类别。

## 9. 风险

| 风险 | 表现 | 应对 |
|---|---|---|
| 转谱噪声上屏 | 谱面是一团碎线，没有参考画面的清爽 | 闸门一最先验证；"原始 / 简化"对比；每首歌可选上屏的轨 |
| 数据覆盖 | 阶段二里大多数歌只能画出音符，没有和弦、段落、小节 | 每层可缺的契约；C3 批量补层；先接受"层数因歌而异" |
| 音画不同步 | 音符过线比声音早或晚 | 逐帧插值的时钟 + 延迟补偿滑块，按设备记住 |
| 变拍 / 奇数拍 | 小节线画错比不画更糟 | 只在网格稳定时画（D4） |
| 人声八度 | 曲线整段偏八度 | 用主唱分离 + 带保护的 RMVPE；没有这条链路的歌先不画曲线 |
| XML 的 `app.js` 是 6000 多行的单体 | 挂场景时牵一发动全身 | 场景本体放独立文件，`app.js` 只加挂钩（B1） |
