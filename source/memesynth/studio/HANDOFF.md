## Spec 摘要

拖一个 `merged.mid` 进来 → 看转谱体检 → 八套音色试听 → 导出整首 WAV。
v2：再拖同一首的 `vocals.wav`，在「人声」里选原唱 / 18 个合成声音 / RVC 模型替代主旋律，整首在后台转，和 kit 同步试听，导出时每套 kit 多一个带人声的 wav。
完整条款见 `SPEC.md`，**改需求前先读那份，新需求进 v2 backlog，本轮不做**。

## 已定决策及理由

1. **界面是本地网页，不是 tkinter。** 这不是审美选择：本仓库的嵌入式 Python 有
   `_tkinter.pyd` 和 `tcl86t.dll` / `tk86t.dll`，但**没有 Tcl 脚本库**（全仓库搜不到
   `init.tcl`），`tkinter.Tk()` 直接抛 `TclError: Can't find a usable init.tcl`。
   Phase 0 实测确认，不要再试 tkinter。
2. **试听用 JS 移植，导出用真 memesynth。** 试听要能八套瞬间切换，每次都回服务端渲染
   做不到。移植版 `engine.js` 已与 Python 逐项对账（见下「不变量」）。导出不走移植版，
   落盘的 wav 与 CLI 同源。
3. **不打包 exe。** 运行时就在仓库里（`runtime/0.5.0/envs/basic/python.exe`，带齐
   numpy / soundfile / pretty_midi），双击 `.cmd` 即可。打包要再塞一份 Python 加 14 MB
   素材，收益为零。
4. **启动器正文全 ASCII。** cmd.exe 按当前代码页解析批处理文件，中文会在部分机器上乱码。
   中文信息一律由 Python 打印（`chcp 65001` + `PYTHONUTF8=1`）。
5. **导出不覆盖**，同名自动 `-2`、`-3`（SPEC §2）。
6. **一套音色失败不影响其余**，逐条报错（SPEC §5）。
7. **人声转换不在工作台的 Python 里跑。** 工作台仍是 envs/basic；折单声道、转 48 kHz、
   Seed-VC / RVC 转换都交给 `source/voiceswap/studio_bridge.py`（envs/highres 子进程，一次一个，
   排队）。工作台只读 voiceswap 的两张目录表（`voices.py`、`rvc_models.py`，纯 dict，用
   `runpy` 读），不 import 任何 voiceswap 代码。
8. **人声按「唱的帧上的 RMS」定音量。** 每个转换结果都对齐到原唱这一项（`remix.py` 的同一套
   算法），所以页面和导出用同一个公式：增益 = −20 dBFS + 滑块 − 原唱的 `activeRmsDb`。
   `VOCAL_TARGET_DB` 在 `server.py` 和 `app.html` 各写了一次，改要两处一起改。
9. **人声替代 kit 的主旋律。** 导出带人声的那个文件里，kit 的 `vocals` 路由被去掉；试听时
   第一次选人声会自动关掉「主旋律」声部（MIDI 里有这条路由时）。七里香的 merged.mid 本来就
   没有 `vocals` 路由。
10. **人声保留和声（2026-11-07）。** bridge 在 `prepare` 时把人声分成主唱和和声，`convert` 时各转一遍，
    再按 voiceswap 定下的做法放回第二声部（`harmony.py`，在七里香上听过五轮定下来的）。转换时间大约翻倍。
    缓存的 `info.json` 记 `pipeline: 2`；之前的缓存打开时，旧的整轨转结果挪到 `pipeline1/`，再重新 prepare。
    没有 karaoke 模型或 envs/roformer 的机器上，退回整轨转。
    pipeline 2 的文件一律比原来低 6 dB 存（bridge 的 `HEADROOM_DB`），`activeRmsDb` 也按存进去的电平量，
    所以增益公式不用改，听到的响度不变。原因是叠回和声后峰值变高：按原电平存，七里香 30 秒的测试片段里
    晓晓有 26 个采样被削顶，留余量后是 0。
    bridge 端到端实测（七里香 239–269 秒，临时目录，不碰真实缓存）：prepare 加分离、IU、晓晓三步都跑通；
    晓晓这一段只用了「整句升八度」，和听评第 5 轮一致。

两个 `.cmd` **正文必须保持纯 ASCII + CRLF**：cmd.exe 按控制台当前代码页解析批处理文件，
中文写在里面会在部分机器上乱码。所有给人看的文字都由 Python 打印。
生成脚本见 git 历史里的 `scratchpad/write_cmds.py`，它会在写出前扫一遍控制字符——
`"%SystemRoot%\System32\find.exe"` 这种路径经过 shell 的 `-c` 会把 `\f` 变成换页符，
真踩过一次。**改 .cmd 请直接用编辑器写文件，不要经过 shell 的 -c。**

`memesynth.cmd` 只在资源管理器启动时 `pause`：靠 `%cmdcmdline%` 里有没有脚本名判断。
在终端里敲、或被别的脚本 `call`，都不会停。两种情况都实测过。

  对账脚本见下「测试命令」。
- **导出路径不走 `engine.js`。** 导出必须用 `batch.export`，它调真正的 `memesynth.render`。
- **`server.py` 只绑 `127.0.0.1`**，`/kits/` 路由只允许 `kits/` 目录下的 `.wav`。
- **分轨相加等于总混音**：导出用同一个 `peak_factor` 衰减总混音和全部分轨。实测差
  110 dB 以下。带人声的那个文件不在这条约束里：它是乐器（与 kit 文件同一电平）加人声，
  只在超过 −1 dBFS 时整体再压一次。
- **人声缓存只写 `work/memesynth-cache/`**，永远不写 XLD 的分析目录（用户在同时用那个库）。
  `/vocal/` 路由只认 16 位十六进制的人声编号和 `[a-z0-9_-]` 的声音名。

## 已知问题

- **页面会比服务活得久。** 关掉启动器窗口后，浏览器里那一页看起来完全正常（音色早就
  载进内存了），一点导出才炸。2026-10-25 真实踩过一次，浏览器只说 `Failed to fetch`。
  现在所有 `/api/` 调用都走 `api()`，网络层失败会统一报「连不上本地服务……双击
  音色工作台.cmd 重新启动」，并在顶部状态栏置红；切回标签页时也会 ping 一次。
  **以后加新的 fetch 一律走 `api()`，不要裸用 `fetch`。**
- `server.py --no-browser` 可以不抢系统默认浏览器（调试时用）。

- 首次打开要载 14 MB 素材（84 个 wav，一套一套加载，第一套到了就能用）。
- 「和声」把 guitar / piano / strings 并成一条，没法单独听钢琴（v2 backlog）。
- `acid` 的 stab 素材只有 0.45 秒，整首歌 58% 的音符会被素材长度截断。这是那套音色的
  已知性格问题，不是 bug，导出时会在结果里报出截断数。
- 服务器启动时会打开系统默认浏览器。换浏览器就自己复制 `http://127.0.0.1:8777/`。

- **v2 人声的实测（2026-10-27，七里香）**：上传 + 整理 4 秒；整首转换晓晓约 2 分钟、IU 约 40 秒，
  两个是排着队一个一个跑的。导出 pluck 加晓晓：人声增益和公式一致（0.6457），超过 −1 dBFS
  时整体正好压 −1.00 dB，拟合残差 −126.6 dB。纯乐器文件不受影响。
- **「去掉 kit 主旋律」在真实数据上还没触发过**：`artifacts/` 里 31 个 merged.mid 都没有 `vocals`
  路由（XLD 不转人声旋律）。`with_voice` 只用合成信号核过（误差 1.5e-8）。
- **RVC 跟随 Seed-VC 的八度判断，但只在先转过一个合成声音时才生效**（同一份人声的缓存里要先有
  `vocals-mono.seedvc.f0-repairs.json`）。先转 RVC 的话，它用自己的守卫。
- 默认片段是 MIDI 音符最密的一段，可能是间奏。第一次选人声时，如果那段人声低于 −40 dBFS，
  会自动挪到人声最响的 12 秒（七里香从 152 秒挪到 166 秒）。
